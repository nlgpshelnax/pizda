# Как коммитить работу команды

Сначала прочитайте [старт команды](docs/team-start.md) и [зависимости](docs/dependencies.md). Для push нужен Git clone и доступ к репозиторию. ZIP не содержит историю Git.

## Одна задача — одна короткая ветка

Перед созданием ветки убедитесь, что текущие правки сохранены. Из чистого checkout:

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/role1-blocker
```

В облачном checkout ветка может называться `work`: не переименовывайте и не сбрасывайте её ради этой инструкции. Проверьте `git status`, при необходимости создайте рабочую ветку от актуального `origin/main`, сохранив свою работу. Не создавайте дополнительный worktree без отдельной просьбы.

Примеры имён: `feat/role2-weather`, `feat/role3-dashboard`, `test/role4-evals`, `docs/role5-pitch`.

## Перед коммитом

1. Выполните проверки своей части: Python — Ruff/pytest, UI — lint/tests/build после появления UI, документы — ссылки/примеры/согласованность.
2. При изменении API перегенерируйте `docs/openapi.json`, обновите примеры и согласуйте совместимость.
3. Выполните `git status` и `git diff`. Проверьте, что нет секретов, `.env`, больших моделей, окружений и случайных артефактов.
4. Добавьте **конкретные** файлы, проверьте staged diff и создайте коммит.

```bash
git add docs/role-1-ai.md
git diff --cached
git commit -m "docs: clarify blocker acceptance criteria"
git push -u origin HEAD
```

Откройте Pull Request на GitHub в `main`; коллега проверяет и объединяет. Команда `git push` сама по себе PR не создаёт. В PR укажите результат, пути/контракты, инструкции запуска, выполненные проверки и ограничения. Назначьте reviewer из затронутой роли. CI сейчас проверяет backend и OpenAPI; UI/evals должны добавить свои checks владельцы, когда появится соответствующий код.

## Получить изменения коллег

На чистой рабочей ветке:

```bash
git fetch origin
git merge origin/main
```

Если есть незакоммиченная работа, сначала сохраните её отдельным коммитом либо используйте понятный вам stash с учётом untracked-файлов. Конфликты разрешайте с владельцем общей модели; при необходимости отмените незавершённый merge через `git merge --abort`. Не используйте force push, `reset --hard`, удаление чужих веток или перезапись всего каталога как способ интеграции.

После merge PR обновите локальный main через `git pull --ff-only`, затем начинайте следующую ветку. Каждый вечер нужен рабочий общий сценарий, а не только несколько независимо запускающихся частей.
