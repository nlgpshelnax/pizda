# Роль 4 — Prompt Engineer / QA & Evals

Ваш результат: извлечение слотов и объяснения проверяемы; команда знает, где система ошибается, и может показать измеренные метрики. Вы владеете промптами и набором из 25–30 краевых сценариев. Роль 1 интегрирует промпты в граф; роль 2 отвечает за истинность цен/времени.

## Старт и зависимости

[Python/LLM/Playwright окружение](dependencies.md). Для JSONL и метрик хватает стандартной библиотеки, Pydantic, pytest и httpx. Отдельная eval-платформа не нужна. Модель/параметры выбираются совместно с ролью 1; version промпта фиксируется в отчёте. Playwright берётся из общего frontend-пакета после его создания.

Сейчас 40 data/provider-тестов уже существуют, но LLM-eval runner и датасет ещё нет. Создайте `prompts/`, `evals/cases.jsonl`, `evals/README.md`, runner в `scripts/` и тесты в первом QA PR. Промпты — версионируемые файлы, не строки, независимо скопированные в нескольких модулях.

## Промпты и контракты

1. **Slot extraction:** только согласованная JSON Schema; evidence из сообщения, YES/Vague/NO, различие missing/null/false, numeric budget без догадок о валюте и базе расчёта.
2. **Patch extraction:** новое сообщение изменяет только явно затронутые поля; старые дети/животные/бюджет не исчезают.
3. **Explainability:** почему подходит, компромиссы, риски; каждый числовой факт привязан к котировке/валидатору. Не обещать визу, ранний заезд, наличие или цену без подтверждения.
4. **Recovery:** невалидный JSON/timeout не стирает state. Данные пользователя и ответы поставщика не могут менять системные правила и требования к источникам.

## Формат eval-кейса

JSONL: `id`, `category`, `turns`, `initial_state`, `expected_slots`, `expected_transition`, `expected_issue_codes`, `forbidden_claims`, `data_mode`, `requires`, `split`. Время задавайте явно (`reference_date`, timezone), чтобы «в ноябре» не меняло смысл при новом запуске. Фиксируйте модель и seed, если backend модели это поддерживает; temperature=0 не гарантирует полной детерминированности.

Пример спецификации будущего кейса, не команда существующего runner:

```json
{"id":"patch-02","category":"context","turns":["На два дня позже"],"initial_state":{"origin":"Москва","destination":"Сочи","check_in":"2026-11-10","check_out":"2026-11-15","guests":{"adults":2,"children_ages":[7],"pets":1}},"expected_slots":{"check_in":"2026-11-12","check_out":"2026-11-17","guests":{"adults":2,"children_ages":[7],"pets":1}},"expected_transition":"requote","expected_issue_codes":[],"forbidden_claims":["старая цена подтверждена для новых дат"],"data_mode":"mock","requires":["agent"],"split":"dev"}
```

Не все случаи могут исполняться текущим каркасом: `requires` отделяет data, agent, frontend, live-provider. До появления компонента ставьте `unrun` с причиной, а не `pass` и не скрытый skip. Разделите на dev и holdout (например 20/10); holdout пишет другой участник и не используется для подгонки промптов. Переформулировки внутри одной семьи нельзя считать независимыми примерами.

## Метрики и отчёт

- Slot accuracy/F1: сравнение по полям с нормализацией и отдельным missing/unknown; отдельно статус слота.
- Context retention: доля patch-кейсов с сохранёнными незатронутыми ограничениями.
- Clarifications: среднее/медиана уточнений до первого пригодного бандла среди завершённых сценариев.
- Stitching errors: число принятых **недопустимых** бандлов / число оценённых бандлов; вместе с долей ложных отказов.
- Latency p50/p95: отдельно парсер, data tools, время до первого пригодного результата; timeout учитывается отдельно, не исчезает из отчёта.
- Unsupported claims: неподтверждённые цены/визовые обещания/ранний заезд на число проверенных объяснений.
- Completion: completed / evaluable; дополнительно total, failed, skipped, unrun и причины, чтобы непокрытые случаи не прятались в знаменателе.

Отчёт: commit SHA, дата, версия модели/промптов, режим данных, машина, число запусков, покрытия и результаты. Сырые логи/артефакты — `.runtime/evals/` (ignored), сводный обезличенный отчёт — `evals/reports/`. Цели согласовать с командой: ориентир 90% завершений внутри покрытия, 0 принятых невозможных стыковок, 0 выдуманных цен; это **цели**, не достигнутые показатели.

## План по дням и приёмка

1. Schema промптов, первые 10 cases, согласование expected outcomes с ролями 1/2.
2. Runner, все 30 cases, отчёт на mock-интеграции; held-out автор отдельно.
3. Пересборка/контекст, замеры LLM, регрессии; первые UI E2E с ролью 3.
4. Полный прогон, ошибки API/LLM, источники и explainability; баги с воспроизводимыми входами.
5. Smoke перед защитой и честный отчёт для роли 5.

Готово: runner возвращает ненулевой exit code на failed обязательных проверках; отчёт не смешивает pass/unrun; команда может повторить прогон по README; каждый исправленный критический баг закрыт содержательной регрессией.
