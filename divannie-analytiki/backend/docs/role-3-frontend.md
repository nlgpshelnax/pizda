# Роль 3 — Frontend Developer

Ваш результат: на защите видно, как агент понимает запрос, уточняет ограничения, собирает поездку и меняет её. Основа — доска: чат слева, живой дашборд справа, слоты YES/Vague/NO, карточки с объяснениями, сценарии раннего заезда/трансфера после покупки.

## Старт и зависимости

[Общий запуск и npm-зависимости](dependencies.md#роль-3-frontend). Сейчас `frontend/` ещё нет: создаёте его в первом UI PR. Стек: React 19, TypeScript 5, Vite 7, TanStack Query 5, CSS Modules; Vitest + Testing Library и Playwright для проверок. Node 24 LTS. Первый PR должен содержать package.json, package-lock.json, scripts и работающую сборку. Остальные участники используют `npm ci`.

Запустите существующий data API или берите JSON из его текущего ответа. `docs/openapi.json` — источник типов; генерируйте `src/api/schema.d.ts`, не правьте его вручную. Чат/session API пока нет: его контракт согласуется с ролью 1. UI-mock храните отдельно от реального API-клиента, с явной меткой режима; не делайте вид, что локальная заготовка является работающим LLM.

## Предлагаемая структура

```text
frontend/src/
  api/           # клиент, generated schema, adapters
  components/    # общие визуальные компоненты
  features/chat/
  features/slots/
  features/trip/
  features/services/
  mocks/         # только UI development
```

Состояние сервера и запросы — TanStack Query; ввод, раскрытые карточки и локальные модалки — React state. Истина о слотах, версии и выборе — backend/session service, не отдельная независимая копия в браузере.

Цена Decimal приходит строкой: не суммируйте денежные компоненты через JS float. Показывайте рассчитанный backend total; Number допустим только для форматирования проверенного значения в пределах согласованных сумм. Все даты отображайте с часовым поясом точки маршрута. Forecast и сезонная статистика визуально различаются; неизвестные условия не становятся галочкой.

Нужны отдельные состояния: начальное, обработка, уточнение, конфликт, варианты, нет вариантов, недоступен сервис, выбранный вариант устарел, demo order, услуга запрошена/подтверждена/недоступна. Текущее data API возвращает только бандлы; остальные состояния появятся с AI/session API.

## План по дням

1. Каркас, типы, split-screen, карточка из существующего mock data API.
2. Слоты и чат на согласованном контракте роли 1; error/loading/empty.
3. Пересборка, сравнение стоимости и сохранение фокуса/скролла диалога.
4. Услуги после покупки, Playwright с ролью 4, проверка доступности клавиатурой.
5. Репетиция на размере экрана защиты, запасной сценарий, freeze визуальных изменений.

## Приёмка и передача

- [ ] Запуск с нуля: npm ci → генерация типов → dev; отдельно build/lint/tests.
- [ ] У mock и snapshot всегда видимый статус; предупреждения о визе/раннем заезде не скрыты.
- [ ] Во время запроса понятно, что происходит; повторный submit не создаёт дубли.
- [ ] Поздний ответ старой версии не перезаписывает новый дашборд.
- [ ] UI не предполагает, что любое 200 означает наличие подходящих вариантов.
- [ ] Роли 4 переданы стабильные accessibility selectors и запуск E2E; роли 5 — порядок демонстрации.
