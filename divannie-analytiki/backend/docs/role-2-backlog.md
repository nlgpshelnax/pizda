# Ваша роль: Backend / Data Engineer

Ваш результат — **агент получает проверяемые данные и может собрать совместимую поездку, даже когда внешние сервисы недоступны на демо**. Вы не пишете Blocker, промпты извлечения, граф диалога или frontend. Но контракты данных, инфраструктура API и фактические причины отказа — ваша ответственность.

Общие инструкции: [старт команды](team-start.md), [зависимости](dependencies.md), [работа с Git](../CONTRIBUTING.md). Для вашей роли достаточно существующего Python dev-окружения; Node и LLM нужны только при общей интеграции. Планы остальных ролей доступны в [README](../README.md).

**Актуальный статус:** [поставка Backend/Data](role-2-final-status.md), [Xotelo](xotelo.md), [демо](demo-backend.md). Исторические состояния 0.3 и этапа 1 ниже оставлены для контекста.

## Что уже подготовлено

- Python/FastAPI-каркас, зависимости с lockfile, конфигурация, CI.
- Pydantic-модели запроса, гостей, стоимости, компонентов бандла и provenance.
- Mock-каталог трёх отдельных котировок одной поездки, API поиска, top-5 по цене.
- Проверки применимости цены, времени, бюджета, питания, звёзд, животных, мест в трансфере.
- Машиночитаемый OpenAPI и примеры для коллег.

Это стартовая поставка: реальных интеграций, исследовательского поиска, полного datamodel доски, агрегированных метрик и услуг после покупки пока нет. TTL-кэш и provider reports уже реализованы.

## Практический порядок на пять дней

**День 1:** отдайте коллегам OpenAPI и рабочий mock. С ролью 1 согласуйте точный запрос, коды ошибок и владельца версии плана. С ролью 3 проверьте отображение одного бандла. Запросите у команды ссылки/доступ к конкретным API; никаких секретов в чат.

**День 2:** подключите доступные hotel/transport API, сделайте нормализацию, provenance, цену по единице расчёта, timeout и contract tests. Начните с одной полной поездки. Если API недоступен — фиксируйте точный blocker и продолжайте отдельный mock-режим.

**День 3:** добавьте SQLite-кэш, OSRM/погоду, расширьте временные проверки. Дайте роли 1 requote при изменении дат/гостей. Проверьте, что питомец с неизвестными правилами не проходит фильтр.

**День 4:** расширьте согласованные направления, проверьте no-results/timeout/401/429/истёкшие цены, пересадки и часовые пояса. Совместно с ролью 4 измерьте ошибки стыковок, p50/p95 и fallback. Добавьте mock-запрос услуги после покупки с честным pending.

**День 5:** зафиксируйте fixtures и версии, прогоните демо без сети и повторный запуск. Покажите пересборку без потери гостей/бюджета, отказ недопустимому варианту и статус источника. Подготовьте резервный сценарий.

## Вопросы, которые нужно закрыть с командой

- Travelpayouts MCP уже доступен команде или нужно использовать REST API? Какой продукт покрывает отели/рейсы?
- Что именно означает «Viajante» на доске и есть ли разрешённый API?
- Есть ли официальный/партнёрский ЖД-доступ, источник виз и тарифов трансферов?
- Какие направления, даты, составы гостей и валюта обязательны на защите?
- Кто хранит session/plan/order и кто подтверждает изменения после покупки?

Эти вопросы не мешают развивать mock-каркас, но без ответов нельзя обещать живые данные.

## Ваш чек-лист перед сдачей

- [ ] Любая цена имеет provider, quote ID, fetched_at/valid_until, валюту, basis и точные параметры.
- [ ] Проверяются оба направления, оба трансфера, hotel occupancy, check-in/check-out и mandatory fees.
- [ ] Ребёнок, питомец и перенос даты вызывают новую проверку котировки.
- [ ] Ошибка API не превращается в «ничего не найдено» и не скрывается синтетикой.
- [ ] Explainability опирается на факты и причины валидатора; цена не генерируется LLM.
- [ ] Общий demo smoke проходит после перезапуска и без внешних API в mock-режиме.
- [ ] Коллеги знают, что реализовано live, что является snapshot, а что mock.
