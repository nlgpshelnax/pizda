# Backend/Data — этап 1: котировки, кэш и пересчёт

Актуальное состояние 0.3.0: [полная поставка Backend/Data](data-delivery.md). Более ранние ограничения ниже относятся к соответствующим этапам; текущие endpoints и блокеры перечислены в итоговом отчёте.
Статус: реализовано в версии 0.2.0. Проверено: 40 тестов, Ruff, HTTP-поиск/requote и сохранение SQLite-кэша после перезапуска сервера. Это работающая локальная data-часть; реальных Travelpayouts/отельных запросов ещё нет. Доступ к конкретному API и его документация не подтверждены. Обязательных новых библиотек не добавлено: SQLite и async runtime входят в Python.

## Что уже работает

- Async `BundleProvider`, `ProviderRunner`: deadline 10 секунд на ожидание/вызов поставщика, concurrency не более 4 на runner, одна повторная попытка только при `unavailable`. 401/403/429 не ретраятся автоматически. Полного circuit breaker пока нет.
- `providers/http.py`: нормализация HTTP/сетевых/JSON-ошибок; клиент и credentials передаёт будущий адаптер, тело ошибки не попадает в API-ответ. Используется стандартная TLS/proxy-конфигурация httpx.
- SQLite TTL-кэш между перезапусками. Ключ включает весь запрос, provider, режим и ревизию; mock-catalog revision вычисляется по содержимому. Истёкший кэш не используется, изменения дат/детей/животных/бюджета не получают ответ другого запроса. TTL не превышает известный срок действия не-mock компонентов.
- Повреждённая запись/ошибка чтения кэша допускает обычный вызов поставщика. Ошибка записи не теряет найденный ответ. Ошибка создания самой БД при старте — конфигурационная ошибка, сервис не объявляет readiness.
- Полная сумма учитывает независимые outbound/inbound transfers. Старый `transfer` поддержан для симметричного маршрута и помечен deprecated в схеме. Для новых котировок задавайте оба поля явно.
- Вместимость номера, политика детей, вместимость обоих трансферов, животные, provenance каждого компонента, provider buffers. Более строгий запас поставщика увеличивает базовый; уменьшить базовый нельзя.
- Статeless requote по полному новому запросу: отдельная котировка, список invalidated компонентов, разница суммы. Это не AI patch и не изменение купленного заказа.

## Воспроизводимый сценарий

```bash
export UV_CACHE_DIR="$PWD/.runtime/uv-cache"
uv sync --frozen
uv run uvicorn trip_data.main:app --host 127.0.0.1 --port 8000
```

Из второго терминала:

```bash
curl --fail http://127.0.0.1:8000/api/health
curl --fail http://127.0.0.1:8000/api/v1/bundles/search \
  -H 'Content-Type: application/json' -d @data/fixtures/search-request.json
curl --fail http://127.0.0.1:8000/api/v1/bundles/requote \
  -H 'Content-Type: application/json' -d @data/fixtures/requote-request.json
```

Каталог содержит три **отдельные синтетические котировки**:

| ID | Условия | Полная сумма |
|---|---|---|
| mock-sochi-001 | Москва → Сочи, 10–15 ноября 2026, 2 взрослых | 73 000 RUB |
| mock-sochi-002-shifted | Москва → Сочи, 12–17 ноября 2026, 2 взрослых | 76 000 RUB |
| mock-sochi-003-child | Москва → Сочи, 12–17 ноября 2026, 2 взрослых + ребёнок 7 лет | 89 000 RUB |

Requote-пример возвращает `price_delta="3000.00"` и `plan_version=2`. Повтор того же запроса возвращает `provider_reports[0].cache_hit=true`, если TTL не истёк. Добавление ребёнка 7 лет требует отдельной третьей котировки; для возраста 6 лет котировки нет, поэтому `new_total` и `price_delta` равны null. Цены не масштабируются арифметически по числу гостей.

Для исходного номера указаны `max_guests=3` и `children_allowed=true`: это свойства синтетического предложения, а не утверждения о настоящем отеле. Даты/наличие в mock не проверяются по текущему календарю; такие fixtures предназначены для повторяемого демо.

## API и ограничения

`POST /api/v1/bundles/search` совместим с прежним запросом; добавлен `provider_reports` (status, attempts, cache_hit, latency_ms). Пустой результат поставщика — HTTP 200 со статусом `empty`. Timeout — 504, прочие нормализованные отказы поставщика — 503 с `detail.code=PROVIDER_FAILURE`; входная ошибка — 422.

`POST /api/v1/bundles/requote` принимает поля SearchInput плюс `previous_bundle_id`. Неизвестный ID — 404. Ответ: previous_total, new_total, price_delta, invalidated_components, search. `new_total` — самый дешёвый пригодный вариант из нового поиска; он может отличаться от прежнего отеля. Выбор конкретного варианта, сохранение selection, сравнение base_version и защита от гонок принадлежат будущему AI/session service. Старый и новый запросы **полные**: merge отсутствующих полей — задача роли 1.

Для новых не-mock бандлов нужен provenance каждого компонента: неизвестный источник или mock внутри реального предложения блокируют результат. У отеля должен быть max_guests; при ребёнке нужна подтверждённая children_allowed. Точное соответствие возраста/детского тарифа определяется областью котировки, а не одним булевым флагом.

`Hotel` пока хранит property и quote вместе. Пересадки, аэропорты/станции, рабочие окна трансферов, профиль визы, FX и настоящая доступность ещё не моделируются полноценно. Сервис по-прежнему разрешает только `TRIP_PROVIDER_MODE=mock`.

## Дальше по роли 2

1. По документации и доступу аккаунта выбрать конкретный Travelpayouts API. Проверить, доступны ли live search/offer или только исследовательские цены. Отельный источник подтвердить отдельно.
2. Добавить нормализованные модели **компонентных** котировок и адаптеры к ним. `BundleProvider` — конечная граница для полного бандла, не утверждение, что Travelpayouts поставляет всю поездку одним ответом. Разделить HotelProperty/HotelQuote, добавить два маршрута трансферов и транспортные сегменты.
3. Подключить Open-Meteo и OSRM по координатам; погода/маршрут не подменяют тариф и availability.
4. Добавить SQLite snapshots, provider-run logs, circuit breaker и согласованную live/cache политику. Сейчас есть TTL cache и reports, а не полная система наблюдаемости.
5. С ролью 1 интегрировать версионированную пересборку и requote выбранного варианта; с ролью 3 — price diff; с ролью 4 — прогон краевых сценариев.
6. Согласовать order/service контракт и ранний заезд/трансфер после покупки. Текущий requote не оформляет эти услуги.
