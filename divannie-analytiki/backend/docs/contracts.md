# Контракты для команды

Актуальное состояние 0.3.0: [полная поставка Backend/Data](data-delivery.md). Более ранние ограничения ниже относятся к соответствующим этапам; текущие endpoints и блокеры перечислены в итоговом отчёте.
## Что работает сейчас

- `GET /api/health` — загрузка непустого каталога проверена при старте.
- `POST /api/v1/bundles/search` — принимает `request` и `plan_version`, возвращает до пяти пригодных бандлов, коды отказов, warnings и ограничения.
- `POST /api/v1/bundles/requote` — новый поиск по полному запросу, разница цены и список зависимых компонентов; [детали](data-milestone-1.md).
- `GET /openapi.json` — источник типов; версия в Git: `docs/openapi.json`.

Пример запроса — `data/fixtures/search-request.json`. Все суммы сериализуются строками Decimal, валюта пока только RUB. `budget` означает **вся поездка для всех гостей**; неоднозначный бюджет должен уточнить AI до вызова API. Отсутствие бюджета не означает нулевой бюджет.

`Bundle.request` фиксирует область применимости цены. `hotel.price` — весь срок/все гости, `outbound.price` и `inbound.price` — все пассажиры за направление; `transfer.price` — одна машина в одну сторону. Полная сумма теперь `hotel + outbound + inbound + outbound_transfer + inbound_transfer`. Старое поле `transfer` остаётся deprecated-совместимостью для симметричного маршрута. Добавлены max_guests/children_allowed, единицы цены и provenance компонентов. Airport/station IDs, тарифные правила детей и сегменты пересадок ещё предстоит реализовать.

`Issue.severity=error` исключает вариант; `warning` отображается в UI. Неизвестное разрешение на животных при наличии питомца — error. Ранний прилёт без подтверждённого раннего заселения — warning об ожидании. Позднее прибытие после окна заселения — error. Бюджет не увеличивается автоматически. В каркасе запас после прибытия 60/90 минут, перед обратным самолётом 120/180 минут, перед поездом 45 минут. Для прибытия поезда базовый запас 15 минут. arrival_buffer_minutes/departure_buffer_minutes поставщика могут увеличить базовый запас. Более короткий запас базовые требования не отменяет.

В `rejected` ключ — ID кандидата, значение — причины. Пустой каталог направления даёт `options=[]`, а не выдуманную поездку. `plan_version` только echo: версия хранится и проверяется будущим AI/session service. Каждый результат содержит provenance и явную метку mock; explanation пока две статические проверяемые причины, не LLM-модуль.

## Передача между ролями

| От кого → кому | Что передать |
|---|---|
| 1 → 2 | точные TripRequest и версия плана; отдельно контракт исследовательского поиска по сезону/vibe |
| 2 → 1 | котировки, полная сумма, ошибки, warnings, provenance; не пользовательские вопросы |
| 2 → 3 | OpenAPI, пример запроса, mock-каталог, коды Issue |
| 4 → 2 | краевые сценарии и ожидаемые ошибки данных/стыковок |
| 2 → 4 | воспроизводимые ответы/коды и метрики поставщиков |
| 5 → 2 | направления демо, сезонность/vibe, подтверждённые справочники |

AI решает, какое ограничение предложить изменить. Data service сообщает факт конфликта, например `OVER_BUDGET`, но не снимает бюджет, не убирает животное и не меняет даты сам.

## Следующие контракты (ещё нет endpoint)

1. **ExploreRequest**: сезон/месяц, origin, vibe, примерные гости; ответ — кандидаты направлений и диапазоны цен с пометкой оценки.
2. **PlanPatch**: changed_fields, base_version; отсутствие поля — сохранить, явный null — очистить. AI пересчитывает зависимости, хранит состояние; stale patch даёт 409.
3. **Live requote**: mock-endpoint уже есть, но настоящая перепроверка availability/цены у поставщика и requote выбранного тарифа ещё не реализованы.
4. **Services**: order ID + запрос раннего заезда/трансфера; состояние requested/pending/confirmed/unavailable. Нельзя показать confirmed без ответа поставщика.
5. **Selection / demo checkout**: version + idempotency key; согласовать с ролью 1. Никаких настоящих платежей.

Генерировать TypeScript-клиент из OpenAPI после выбора инструментов ролью 3. Chat endpoints не добавлены намеренно: схема управления графом должна принадлежать роли 1.

Provider reports, HTTP-коды ошибок, новые поля и пример пересборки описаны в [этапе Data 1](data-milestone-1.md).

Для планов/заказов теперь есть persisted data endpoints с version/CAS — см. [контракты версии 0.3.0](data-delivery.md#основные-endpoints). Диалог/граф принадлежат роли 1.
