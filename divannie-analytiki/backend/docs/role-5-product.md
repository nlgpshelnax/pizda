# Роль 5 — Product Lead / Pitcher

Ваш результат: команда делает согласованный продукт и показывает понятный сценарий с доказательствами. Вы владеете сценарием защиты, продуктовыми критериями и базой знаний о направлениях. Вы не обещаете готовность API или улучшение бизнес-метрик без измерений.

## Старт и инструменты

Для документов достаточно Git и Markdown/CSV-редактора: [получить проект и коммитить](team-start.md). Общий backend можно запустить по [инструкции](dependencies.md), но установка Python/Node не обязательна для работы над питчем. Слайды можно готовить в любом редакторе; в Git положите текст, сценарий и переносимый PDF/экспорт либо доступную ссылку на исходник.

Создайте `pitch/pitch.md`, `pitch/demo-script.md`, `pitch/limitations.md`, `data/knowledge/destinations.csv`, `data/knowledge/README.md` в первом PR. Сейчас эти файлы ещё не созданы. Задачи и исходные факты храните в репозитории, чтобы архив содержал всё необходимое для продолжения работы.

## Продуктовая рамка

Пользователь хочет организовать поездку целиком, а не вручную согласовывать отель, дорогу, трансфер и условия. Ценность: одно обращение, понятные компромиссы, согласованные компоненты и пересборка без повторного ввода данных. Для Островка это гипотезы роста конверсии, среднего чека и доли дополнительных услуг. Их проверка требует данных/эксперимента; на защите показываем технические proxy-метрики и предлагаем дизайн A/B, не заявляем рост выручки как установленный факт.

## База знаний

Согласуйте с ролью 2 CSV/JSON schema до наполнения. Минимальные поля: destination_id, city, country, timezone, month, vibe_tags, activity_tags, seasonal_notes, source_url, checked_at, confidence, caveats. Для температур/моря/снега указывайте тип данных (forecast/climatology), единицы, период и источник. Не называйте климатическую среднюю прогнозом на конкретную поездку.

Теги — небольшой словарь (`beach`, `city_walks`, `ski`, `family`, `nightlife` и согласованные русские подписи), а не сотни несовместимых формулировок. «Тихо», «безопасно», «подходит детям» требуют оснований и оговорок. Справочник помогает исследовать направление; он не подтверждает отельные условия, визовый допуск или цену. Гражданство/документы пользовательские, их нельзя выводить из языка запроса.

## Сценарий защиты: ориентир 5 минут

| Время | Что показать | Кто обеспечивает |
|---|---|---|
| 0:00–0:35 | Боль ручной сборки поездки и продуктовое обещание | 5 |
| 0:35–1:15 | Размытый запрос, слоты и необходимое уточнение | 1/3/4 |
| 1:15–2:10 | До пяти бандлов, полная сумма, причины, риски и происхождение данных | 2/3 |
| 2:10–3:10 | «На два дня позже», сохранение контекста, изменения цены/компонентов | 1/2/3 |
| 3:10–3:45 | Demo order и запрос раннего заезда/трансфера | 1/2/3 |
| 3:45–4:25 | Невозможная стыковка либо отказ API с честным fallback | 2/4 |
| 4:25–5:00 | Измеренные результаты, ограничения и следующие шаги | 4/5 |

Это целевой сценарий: сейчас из него реализован только поиск бандла из mock-каталога. К дате репетиции проверьте каждый шаг и исключите неподтверждённые claims, не скрывая недостающую функцию. Фразы/даты согласуйте с фактическим покрытием каталога. Если новых дат в каталоге нет, правильный результат пересборки — отсутствие котировки, а не старая цена.

Для демонстрации сдвига роли 2 нужно добавить **отдельную** котировку новых дат, роли 1 — patch без потери гостей, роли 3 — diff, роли 4 — проверку. Продуктовая роль заранее обеспечивает, что эти зависимости есть в общем main.

## План по дням

1. Согласовать scope/покрытие/тайминг; определить историю пользователя; закрыть спорные названия источников с ролью 2.
2. Заполнить первые направления/сезонность, написать pitch v1 и черновик demo script.
3. Репетиция рабочего пути и пересборки; проверить видимость объяснений и ограничений.
4. Получить отчёт QA, собрать слайды, подготовить резервную запись и ответы о рисках.
5. Две репетиции с таймером, freeze версии; проверить запуск без истории браузера и с новой сессией.
